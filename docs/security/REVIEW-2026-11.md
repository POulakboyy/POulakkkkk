## 2. Méthode

- **Lecture intégrale** du code des composants ci-dessus, en suivant les données non fiables
  depuis leur point d'entrée (trame WebSocket, lien `pouxis://`, Markdown saisi ou synchronisé,
  archive importée) jusqu'à leur puits (stockage disque, DOM, IPC, journal).
- **Grille** : OWASP Top 10 (injection, XSS, contrôle d'accès, configuration), STRIDE du modèle
  de menaces, critères spécifiques demandés (comparaisons en temps constant, limites de taille et
  de débit, traversée de chemin, déni de service WebSocket, contrôle d'origine, fuite de secrets
  dans les journaux, conteneur non privilégié, CSP, capacités Tauri, liens profonds).
- **Recherche systématique de puits dangereux** dans `apps/` et `packages/` :
  `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `eval`,
  `new Function`, `document.write`, `srcdoc`, `fetch`, `window.open` — aucun usage applicatif de
  puits HTML ; aucun `fetch` dans le client.
- **Vérification dynamique** de la CSP de production : build de production dans un répertoire
  temporaire, servi avec les en-têtes exacts de `vercel.json` **plus Trusted Types appliqués**
  (`require-trusted-types-for 'script'; trusted-types 'none'`), puis parcours automatisé
  (Chromium, Playwright) des neuf routes avec activation des premiers contrôles de chaque vue.
  Résultat : aucune violation CSP ni Trusted Types, aucune erreur de page ; une affectation
  `innerHTML` de contrôle est bien bloquée.
- **CodeQL** : la CLI `gh` n'est pas utilisable depuis l'environnement de revue ; les alertes
  n'ont donc pas été consultées. Le raisonnement a porté sur les mêmes classes de failles
  (requêtes `security-extended` du workflow `codeql.yml`) directement dans le code.
- **Corrections** limitées aux fichiers sous la responsabilité de la revue, chacune couverte par
  des tests ; les constats ailleurs sont transmis aux responsables des fichiers (section 5).

## 3. Synthèse du modèle de menaces

Les acteurs restent ceux du [modèle de menaces](./THREAT_MODEL.md#1-périmètre-et-hypothèses).
Pour cette revue, les plus pertinents sont :

- **A2 — relais malveillant ou compromis** : il ne doit rien lire (chiffrement de bout en bout)
  et toute modification doit être détectée (AAD). Il peut toujours retenir ou supprimer des
  enveloppes, et observe les métadonnées (horaires, tailles arrondies, nombre d'appareils).
- **Détenteur d'un jeton d'espace sans la phrase secrète** (jeton divulgué, appareil retiré) :
  il peut écrire dans le journal du relais, mais ne peut produire aucune charge utile acceptée
  par les clients.
- **Client hostile du relais** (internet) : il cherche à épuiser les connexions, la mémoire ou le
  disque, ou à deviner un jeton.
- **A4 — contenu injecté** : Markdown d'une note ou d'une tâche (saisi, collé ou synchronisé),
  titres de nœuds exportés en SVG, lien `pouxis://` forgé par une page web.

Garanties vérifiées et conformes :

- AES-256-GCM, IV aléatoire de 96 bits par message (SP 800-38D §8.2.2), préfixe de format
  authentifié, AAD canonique liant **espace, id, HLC et nœud** de chaque enveloppe ; le client
  refuse en plus toute opération dont l'origine diffère du nœud de l'enveloppe ou dont l'horloge
  dépasse celle de l'enveloppe (`sync/protocol.ts`, `envelopeToOps`).
- Clé d'espace : PBKDF2-HMAC-SHA256, 600 000 itérations (plancher et plafond vérifiés), sel de
  128 bits dérivé de l'identifiant d'espace avec séparation de domaine, phrase secrète normalisée
  NFKC, au moins 15 caractères ; clé AES non extractible conservée comme objet opaque, phrase
  secrète jamais persistée et effacée de l'état React après usage.
- Rejeu : les poussées sont idempotentes sur l'id d'enveloppe (relais) et d'opération (réplica).
- Relais : jetons HMAC-SHA256 vérifiés en temps constant avant tout décodage, rotation des
  secrets, secret d'au moins 32 caractères hors développement ; trames limitées (`maxPayload`),
  compression désactivée (pas de bombe de décompression), limitation de débit par connexion
  avec fermeture après récidive, quota disque par espace, délai de `hello`, contre-pression et
  fermeture des consommateurs lents ; noms de fichiers = SHA-256 de l'espace (aucune traversée
  possible), fichiers `0600`, répertoire `0700` ; journaux sans charge utile, jeton, IP ni
  identifiant en clair ; image Docker non root, système de fichiers en lecture seule possible,
  `cap_drop: ALL`, `no-new-privileges`.
- Tauri : `withGlobalTauri: false`, CSP sans `unsafe-eval` ni script en ligne, capacités par
  fenêtre et par plateforme (aucune permission `fs`, `shell`, `http` ni `opener`), commandes
  natives explicites, programmes système lancés sans shell ; liens `pouxis://` analysés en Rust
  (schéma, type, identifiant `[A-Za-z0-9_-]{1,128}`, URL reconstruite) puis revérifiés côté web.
- Web : rendu Markdown construit en éléments React (jamais de chaîne HTML), liens limités à
  `http(s):` (et `mailto:` dans les idées), `rel="noopener noreferrer"` ; export SVG échappé
  (`escapeXml`), coordonnées numériques ; champs réservés (`__proto__`, `constructor`,
  `prototype`) refusés par le moteur de synchronisation.
- Archives (CLI) : noms d'entrées ZIP validés, tailles par entrée et totale bornées,
  décompression bornée, noms de notes réduits à `[a-z0-9-]`.

### Détail des corrections

- **S-01** — `Session.handlePush` vérifie que chaque enveloppe porte le nœud authentifié avant
  tout stockage ; une poussée mixte est rejetée en bloc. Le client officiel ne pousse que ses
  propres opérations (`opsSince(…, { origin: node })`) et n'est pas affecté. Test :
  `test/hardening.test.ts` (« refuses envelopes attributed to another node »).
- **S-02** — `AddressCounter` compte les connexions vivantes par adresse ; au-delà du plafond, la
  mise à niveau WebSocket est refusée en `429` (métrique `connections_rejected_total{reason="address"}`).
  Derrière un mandataire inverse, `POUXIS_TRUST_PROXY=true` prend la **dernière** entrée de
  `X-Forwarded-For` (celle ajoutée par le mandataire ; les précédentes sont contrôlées par le
  client). L'adresse n'est jamais journalisée.
- **S-05** — `connect-src 'self' ipc: http://ipc.localhost wss: ws://localhost:* ws://127.0.0.1:*`
  (production), même logique en développement.
- **S-06** — ajout de `Cross-Origin-Opener-Policy: same-origin`,
  `Cross-Origin-Resource-Policy: same-origin`, `Strict-Transport-Security: max-age=63072000`
  (sans `includeSubDomains` ni `preload`, qui engageraient les autres sous-domaines), de
  `frame-src 'none'` et `manifest-src 'self'`, et d'un en-tête
  `Content-Security-Policy-Report-Only: require-trusted-types-for 'script'; trusted-types 'none'`.
  Aucun en-tête existant n'a été affaibli.

### Faisabilité de Trusted Types

Dans le bundle de production, les seules affectations `innerHTML` sont internes à React DOM et
inatteignables par l'application : création d'un élément `<script>` (jamais rendu)
et `dangerouslySetInnerHTML` (jamais utilisé). Le parcours automatisé avec Trusted Types
**appliqué** n'a relevé aucune violation. L'en-tête est publié en mode `Report-Only` pour un
cycle de version afin d'observer les parcours non couverts ; il pourra ensuite rejoindre la CSP
appliquée. Aucune politique Trusted Types n'est nécessaire (`trusted-types 'none'`).

### CSP de `index.html`

Aucune balise `<meta http-equiv="Content-Security-Policy">` n'est ajoutée, volontairement : en
production web, l'en-tête HTTP fait foi (une balise `meta` ne peut exprimer ni
`frame-ancestors` ni le mode `Report-Only`) ; dans Tauri, la CSP de `tauri.conf.json` est
injectée par le shell ; en développement, le préambule de rafraîchissement de React est un
script en ligne qu'une CSP stricte bloquerait. Le document ne contient aucun script ni style en
ligne et reste donc compatible avec `script-src 'self'`.

## 6. Risques résiduels

- **R-01 — Rétention par le relais.** Un relais malveillant peut retenir, retarder ou supprimer
  des enveloppes ; les curseurs et le journal d'audit ne le détectent que partiellement.
- **R-02 — Déni de service.** Le plafond par adresse est désactivé par défaut pour ne pas
  limiter toute une instance derrière un mandataire non déclaré ; tant qu'il n'est pas configuré,
  seul le plafond global protège. Les attaques volumétriques relèvent de l'infrastructure.
- **R-03 — Métadonnées.** Horaires, tailles arrondies (Padmé), nombre d'appareils et adresse IP
  (au niveau du mandataire) restent visibles du relais.
- **R-04 — Appareil déverrouillé ou script de même origine.** Le jeton et la clé d'espace sont
  utilisables par tout code de l'origine ; la CSP stricte et l'absence de puits HTML sont la
  défense principale. Les chaînes JavaScript (phrase secrète) ne peuvent pas être effacées de la
  mémoire de façon garantie.
- **R-05 — Clé d'espace unique et durable.** La même clé chiffre toutes les enveloppes d'un
  espace ; la limite de 2³² messages par clé avec IV aléatoire (SP 800-38D §8.3) est hors
  d'atteinte en usage réel, mais aucune rotation de clé d'espace n'existe encore.
- **R-06 — PBKDF2.** Résistance limitée face au calcul massivement parallèle comparée à Argon2id
  (migration prévue, ADR-SEC-001).
- **R-07 — `freezePrototype` Tauri désactivé.** L'activer durcirait contre la pollution de
  prototype mais n'a pas pu être testé sur les shells natifs pendant cette revue.
- **R-08 — Image de base Docker non épinglée par empreinte** (`node:22-alpine`) ; à épingler par
  `@sha256:` dans la chaîne de publication avec mise à jour par Dependabot.
- **R-09 — Alertes CodeQL non consultées** (voir méthode) ; à rapprocher de cette revue lors de
  la prochaine exécution du workflow.
